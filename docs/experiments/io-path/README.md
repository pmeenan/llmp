# M0 I/O path comparison — 2026-09-21

This experiment compares regular-file storage paths on `spark`, including
the owner's requirement that payload transfers use DMA without CPU copies.
It measures transfer completion, GPU access to the resulting allocation,
page-cache use, small and sparse reads, concurrent GPU work, memory pressure,
and sustained SSD reads. It is a synthetic storage experiment, not a model
throughput or end-to-end page-in benchmark.

## What is being compared

The filesystem interface, submission interface, memory allocation, and copy
path are separate choices. An ordinary file can use direct DMA into memory
the GPU consumes in place; removing the filesystem is not a prerequisite.

| Probe mode | File access | Destination / GPU path |
| --- | --- | --- |
| `buffered` | `pread`, OS page cache | Registered host staging → CUDA copy → device VMM |
| `direct` | `O_DIRECT` + `pread` workers | Registered host staging → CUDA copy → device VMM |
| `uring` | `O_DIRECT` + registered-buffer `io_uring` | Same staging and device VMM |
| `cufile` | cuFile compatibility mode, direct descriptor | cuFile-managed transfer to device VMM |
| `inplace` | `O_DIRECT` + `pread` workers | System allocation, GPU accesses that allocation |
| `hostvmm` | `O_DIRECT` + `pread` workers | Host-NUMA CUDA VMM, GPU accesses the same allocation |
| `uring_hostvmm` | `O_DIRECT` + registered-buffer `io_uring` | Host-NUMA CUDA VMM, GPU accesses the same allocation |
| `write` / `hostvmm_write` | Direct writes into an exclusively created scratch file | GPU-generated bytes, with / without a CUDA staging copy |

`io_uring` here uses normal kernel NVMe I/O, registered buffers, one ring
owner, one submission per request, completion polling with host yields, and
ordinary interrupt-driven storage completion. It does **not** enable
SQPOLL or IOPOLL, use NVMe passthrough, or bypass the kernel. Its polling
CPU cost is a measured tradeoff; this probe does not settle the runtime's
executor or sleep/wake policy.

Both device and host VMM use `cuMemCreate`, a virtual address reservation,
`cuMemMap`, and explicit access grants. Host allocations use
`CU_MEM_LOCATION_TYPE_HOST_NUMA`, ID 0 on this target, with access for both
host and GPU. Each physical handle is independently mapped at the queried
2 MiB minimum granularity. A larger contiguous I/O spans several handles.
The experiment never passes an absent mapping to a kernel or I/O request.

### Measurement endpoints

Allocation, mapping, access grants, host registration, cuFile setup,
preflight content verification, and cache preparation precede timing.
Device VMM buffers are fully backed and reusable before the first timed
read. Results therefore exclude allocation/map/access latency, import/hash
cost, scheduler admission, model work, and cancellation/reclaim behavior.

For staged reads, completion includes the CUDA copy completing. For in-place
reads, it is the direct read completion into GPU-accessible memory; the
uring variant also completes a CUDA event on the slot's otherwise empty
stream. Neither endpoint includes a model consuming the bytes. A separate
resident scan measures that consumption path: repeatedly read every word
of a 256 MiB allocation on the GPU and materialize a per-thread reduction.
This is larger than the small transfer buffers, and its measured disk bytes
must be near zero. It is still a scan, not GGML or quantized GEMM.

Latency is host wall time from individual submission to observed completion,
including queueing within the selected depth. Worker setup and final drain
are included in aggregate throughput. Percentiles use the sorted sample at
`floor(p*(n-1))`; no trimming or timer subtraction. Aggregate GB/s is decimal
bytes per elapsed second. Histograms have 10 µs buckets, with >=100 ms in
the final bucket; exact p50/p95/p99/max are recorded separately.

Every read mode verifies all words in every slot before timing and in each slot's
final contents after timing. A deliberately corrupted word must yield exactly
one mismatch, followed by a clean check after restoration. This does not hash
every timed transfer. Writes generate offset-specific payloads on the GPU,
wait for GPU completion, issue direct writes, drain all workers, and call
`fdatasync`; every written word is then read back and GPU-verified. Write
GB/s includes GPU generation and any staging copy but excludes the separately
reported final `fdatasync`. Each write test creates a new 4 GiB file exclusively,
never opens an existing destination for modification, and stops at EOF.
These short writes do not measure steady-state NAND write speed after SLC
cache exhaustion, power-loss recovery, or a complete spill publication protocol.

### Cache, pressure, and load controls

"Cold" means this clean test file has zero OS-cache pages according to
`mincore` after file-specific `POSIX_FADV_DONTNEED`. No global cache flush is
used. Direct reads can wrap the file while still bypassing page cache;
buffered cold reads stop after one traversal to avoid mixing warm laps.
Warm buffered tests explicitly load the full file first. Controller and
filesystem-metadata caches are not reset. `sparse` reads 64 KiB every 2 MiB,
at most once through the file, stopping at EOF or the requested duration,
from an initially empty file cache.

File cache occupancy comes from `mincore` on that exact file. Physical I/O
bytes come from `/sys/block/nvme0n1/stat`, so they include other activity on
the root disk and are supporting evidence, not an exact per-file meter.
Read amplification here means block-device bytes / requested file bytes;
it is not flash-internal amplification, or a prediction from actual expert
selection traces. Small rounding/background differences are reported honestly.

Pressure is **100 GiB of separately allocated, GPU-touched CUDA memory**,
held for the process lifetime. An aggregate headroom guard counts test
buffers, telemetry samples, background data, and at least 12 GiB of remaining
OS headroom before allocation. The memory background kernel repeatedly scans
an independent 1 GiB allocation. The compute background kernel does a fixed
number of register FMA operations and writes a small result. Both use their
own stream, one completed launch at a time. Matched no-I/O controls measure
completed kernels per second; throughput effects are synthetic, not tokens/s.
Process CPU seconds omit interrupt and external kernel-worker CPU time.
Clocks and CPU placement are not locked; results are ranges, not guarantees.

## Results

### Sequential reads and queue sizing

The following are **ranges over three runs**, with the observed controller
interrupt-coalescing setting unchanged: feature 8 = `0x107` (100 µs
aggregation timer, eight-completion threshold). Each run requests three
seconds, except cold buffered traversal also stops at EOF. All rows use
2 MiB requests and four outstanding slots/workers unless noted.

| Path | GB/s | Per-read p50, µs | Per-read p99, µs | File cache afterwards |
| --- | ---: | ---: | ---: | ---: |
| Buffered, initially cold | 1.504–1.779 | 4387–5214 | 8934–11229 | 4.60 GiB mean |
| Buffered, fully warm | 35.083–35.470 | 234–239 | 255–280 | 32 GiB |
| Direct + workers + CUDA staging copy | 12.819–13.257 | 598–633 | 1149–1236 | 0 |
| Direct + workers + host VMM in place | 12.517–12.984 | 614–664 | 1262–1375 | 0 |
| cuFile compatibility + device VMM | 12.971–13.673 | 589–629 | 1102–1210 | 0 |
| Direct + io_uring + CUDA staging copy | 14.947–14.955 | 558 | 614–631 | 0 |
| Direct + io_uring + host VMM in place | **14.903–14.968** | **558** | **608–634** | **0** |

The warm buffered row is a DRAM-cache result, not SSD bandwidth, and used
about four process CPU-seconds per elapsed second. The two io_uring paths
used about one; worker paths used less than or around one. Those figures
are whole-process CPU use, not CPU-copy byte counts or full system CPU cost.
At queue depth eight, cuFile reached 13.945–14.723 GB/s but its p50 rose to
1121–1178 µs. The simpler in-place path needs neither cuFile's emulation nor
its hidden transfer-buffer policy to reach the higher file-path result.

Queue depth for `uring_hostvmm`, 2 MiB requests:

| Outstanding requests | Total destination bytes | GB/s | p50, µs | p99, µs |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 2 MiB | 11.579–11.614 | 176–177 | 214–216 |
| 2 | 4 MiB | 14.625–14.845 | 279 | 350–395 |
| 4 | 8 MiB | 14.903–14.968 | 558 | 608–634 |
| 8 | 16 MiB | 14.960–14.966 | 1116 | 1196–1217 |

Two requests give almost all the bandwidth at half the four-request
completion latency. Four is a bulk-transfer setting; eight adds queueing
without a material bandwidth gain here. With 8 MiB requests at depth four,
bandwidth remained 14.952–14.966 GB/s but p50 increased to 2233–2234 µs.
Bigger transfer batches therefore do not justify bigger independently
reclaimable extents. A latency-first path should avoid waiting for a large
batch when the first 2 MiB dependency could become usable earlier.

### GPU consumption and cache amplification

Repeated GPU scans over 256 MiB of already populated memory:

| Backing | GPU scan GB/s, three-run range |
| --- | ---: |
| Device VMM | 241.869–243.331 |
| Host-NUMA VMM | 242.016–242.598 |
| Ordinary aligned system allocation | 161.858–163.087 |

Host-backed VMM matched device VMM in this test while avoiding the transfer
copy. Ordinary system allocation is not an interchangeable performance
baseline. The experiment does not isolate whether page size, translation,
or another allocation property causes that difference, and it does not
establish GGML/GEMM performance on these pointers.

Direct modes left no file pages in the OS cache. Buffered cold reads retained
pages for the newly read data; the probe reuses its small destination slots,
so this is measured cache growth alongside the mapped buffers, not an
assertion that a full 32 GiB duplicate GPU model was also allocated. A real
full-model load would need to account for both useful backing and retained
file pages in the same physical budget.

The sparse probe requests 64 KiB every 2 MiB. It showed approximately 1×
block-level read amplification, including for buffered reads: this pattern
did not trigger a large readahead penalty. Buffered sparse throughput varied
0.180–0.317 GB/s; direct workers 0.278–0.319; host-VMM workers 0.215–0.326.
The small-request completion floor and CPU scheduling dominate these values.
This is not evidence that all sparse layouts have 1× amplification.

### Concurrent work and memory pressure

Two runs per condition, 2 MiB requests at depth four:

| Condition / path | SSD GB/s | Background memory scans/s |
| --- | ---: | ---: |
| Memory scan alone, no pressure allocation | — | 210.963–211.630 |
| Memory scan + in-place io_uring | 14.915–14.963 | 190.295–191.634 |
| Memory scan + staged direct workers | 12.570–12.756 | 169.956–170.277 |
| Memory scan alone, 100 GiB held | — | 222.628–223.630 |
| Memory scan + in-place io_uring, 100 GiB held | 14.906–14.966 | 199.967–200.967 |
| Memory scan + staged direct workers, 100 GiB held | 11.982–12.317 | 175.629–177.958 |
| Memory scan + cuFile compatibility, 100 GiB held | 12.422–13.110 | 174.299–179.283 |

The in-place path maintained SSD bandwidth but reduced the independent
memory scan's rate by roughly 10% against its matching control. Staged worker
paths reduced it by roughly 20–21% at their measured I/O rates. These are
whole-path comparisons with different SSD rates, not an isolated copy-cost
measurement. There is one shared DRAM budget and bandwidth pool; eliminating
CPU copies does not eliminate memory-bandwidth contention.

The compute-only control completed 1279.465–1279.797 kernels/s. With in-place
I/O it completed 1274.774–1280.441 kernels/s while reading 14.913–14.970 GB/s.
That test did not expose a substantial compute-rate loss. With 100 GiB held
but no background kernel, in-place I/O reached 14.952–14.959 GB/s.

The separate full-file pressure test traversed all 32 GiB with buffered I/O
while holding 100 GiB, rather than stopping after the small amount read in
a three-second test. It reached 1.728–1.776 GB/s and retained about 16 GiB
of file cache at completion; the remainder had to be reclaimed as traversal
progressed. The analyzed telemetry included page-scan/reclaim and swap
counters. This validates the shared-budget concern without allocating a
second full GPU model or forcing an OOM.
Across those two runs, global counters recorded 9,362,992 pages reclaimed by
kswapd, no direct reclaim, and ten 4 KiB pages swapped out (40 KiB); these
are whole-host observations, not attribution of swapped contents to the
probe. Minimum sampled MemFree was 0.659 GiB while reclaimable MemAvailable
at the timing endpoints remained about 17 GiB. Available memory and unused
physical pages must not be presented as the same measure.

A preliminary 104 GiB pressure phase was excluded in full after the guard
rejected one process whose current headroom was insufficient. All reported
pressure conditions were rerun at 100 GiB; the completed baseline matrix
was unaffected. There was no failed allocation or OOM in that rejection.

### Sustained reads and bounded spill writes

The continuous in-place io_uring run completed **180.000414 s**, reading
**2,693,189,861,376 bytes at 14.962131 GB/s**. Its per-request p50/p95/p99
were **558.061 / 586.365 / 645.644 µs**; the maximum was **9.872 ms**.
The long run therefore exposes a tail that short medians do not describe.
File cache stayed at zero. The root-device counter exceeded requested bytes
by about 8 MiB over 2.69 TB; it is not a per-file counter.

One-second disk-stat intervals, excluding the first two and last two
intervals to avoid setup/drain, ranged **14.914–14.982 GB/s** (176 intervals).
The early and late approximately 30-second means were **14.962 and 14.961
GB/s**. Across the run, SSD sensors ranged **48.85–58.85°C**. No sustained
throughput decline was observed; this does not establish behavior at every
ambient temperature or under sustained writes.

Three fresh 4 GiB write bursts per mode, each followed by `fdatasync` and
full direct-read/GPU verification:

| GPU → SSD path | Burst GB/s | Final fdatasync, ms |
| --- | ---: | ---: |
| GPU generation → CUDA staging copy → direct write | 10.913–11.131 | 3.346–4.022 |
| GPU generation into host VMM → direct write of same bytes | **11.641–11.963** | **3.312–3.838** |

These rates include GPU payload generation and exclude the separately
reported flush; the flush occurs once per 4 GiB burst, not once per 2 MiB
extent. Use one bounded spill queue initially, at most four 2 MiB requests
in flight (8 MiB of leased source backing), and prioritize demand reads.
This is conservative queue/budget guidance, not a measured mixed read/write
optimum. The resident source remains charged and leased until transfer
completion and the required recoverable-state publication. No extra host
staging is needed for the tested host-VMM path.

Expose spill bytes/s and bytes/day and bound retained spill capacity/lifetime;
do not adopt 12 GB/s as a sustainable-write allowance. NAND/SLC exhaustion,
mixed read/write tails, full state-publication durability, and the device's
applicable endurance rating remain inputs to M6's spill policy. No endurance
permission or lifetime-write budget is invented from this short test.

### Interrupt coalescing: a large small-read latency improvement

The target reported NVMe feature 8 = `0x107`: a 100 µs aggregation timer
and eight-completion threshold. The controller reports the feature as
changeable, and I/O vector 1 has coalescing enabled (the admin vector does
not). A/B runs alternate the observed setting and zero three times, with
readback after every change. Feature zero disables coalescing. The original
**`0x107` was restored and verified** at the end; no saved setting, reset,
or driver change was made.

| Sequential direct host-VMM I/O | Original p50, µs | Coalescing off p50, µs | Original GB/s | Coalescing off GB/s |
| --- | ---: | ---: | ---: | ---: |
| 4 KiB, depth 1 | 199.919–199.935 | **6.655–6.816** | 0.020 | 0.589–0.605 |
| 64 KiB, depth 1 | 199.934–199.935 | **11.584–11.888** | 0.328 | 5.448–5.566 |
| 2 MiB, depth 1 | 171.503–172.143 | 170.799–171.327 | 11.753–11.760 | 11.864–11.890 |
| 2 MiB, depth 4 | 558.045–558.109 | 558.108–558.125 | 14.956–14.964 | 14.951–14.963 |

With coalescing disabled, 4 KiB p99 was 7.568–7.776 µs and 64 KiB p99 was
12.496–12.832 µs. These are **sequential requests**, with OS file cache
excluded but controller caches/prefetch left alone. They are not cold-NAND
random-read latency claims. Large requests already create enough completions
to avoid much of the timer penalty. Buffered 2 MiB/depth-four cold reads also
improved, from 1.561–1.760 to 4.888–5.049 GB/s; they still involve the CPU
payload copy and page cache.

The cost is more interrupts. Whole-probe snapshots (including setup) at
2 MiB/depth four went from about **11.2–11.3 thousand NVMe interrupts/s** to
**89.9–91.4 thousand/s**, while the bulk transfer rate stayed near 15 GB/s.
Do not infer a system CPU-cost bound from the polling thread already consuming
one core. This result makes disabling coalescing a useful explicit deployment
tuning option for small demand reads; the inference runtime must not change
the root controller's global policy silently.

The first exploratory control attempt exposed two nvme-cli 2.8 integration
details: `-v` means verbosity, while `--value` / `-V` sets the feature; a zero
get-feature value is printed without `0x`. That attempt was excluded. The
original value was restored with explicit long options and verified before
the complete A/B comparison was rerun. The retained script uses long options,
accepts both numeric output forms, records the original value before mutation,
bounds control calls, and restores on ordinary exit, failure, HUP, TERM, or
INT while protecting cleanup against another signal. Hard kill/power loss is
outside a process-level `finally` guarantee; the audit preserves the original
value for recovery. See RE-003.

## DMA evidence

The selected in-place path contains no host payload copy and no CUDA payload
copy: the direct-I/O buffer address is the GPU-consumed VMM address. CPU work
still performs file lookup, submission, bookkeeping, and completion handling.
That control work is different from moving tensor bytes through CPU copies.

Linux documents direct reads as storage transfers into the caller's buffer.
The potential exception relevant here is DMA bounce buffering: SWIOTLB can
DMA into an intermediate allocation and copy through the CPU. An isolated
tracefs instance records `swiotlb:swiotlb_bounced` throughout the retained
experiment, with start/end markers, trace enable state, and per-CPU overrun
statistics. No existing tracing session or driver setting is altered.
The aggregate trace outcome is recorded below; the raw trace stays outside Git.

The captured trace contains **zero SWIOTLB bounce events**, both markers,
event-enabled and tracing-on values of **1**, and zero overruns/dropped
events across all **20 CPU buffers**. Its 1431.727-second window includes
the retained measurements and excluded exploratory/retry activity. The
instance was disabled and removed after capture.

Together, exact-length direct completions, empty file cache, matching disk
traffic, GPU content checks on the destination, and the bounce trace test the
actual path. This is evidence for the measured kernel/device/allocation
combination, not a claim that every `O_DIRECT` implementation or driver can
never fall back or bounce. A changed provider/filesystem must earn the same
capability; silently enabling CPU payload copies violates the selected policy.

## Files versus raw block and other options

| Option | What it changes | Disposition |
| --- | --- | --- |
| Buffered files | Page-cache reuse; read syscall copies cached data into the caller's buffer | Comparison/control path; duplicate occupancy competes with managed memory |
| File `mmap` | GPU/system page-table access may avoid the read-syscall copy, but pages belong to OS cache and faults/reclaim | Not benchmarked; does not supply the current explicit VMM backing lifecycle |
| Direct files + native I/O | Bypasses file page cache; can DMA into our final GPU-accessible allocation | Measured candidate, retains ordinary artifact files |
| Raw block device + direct I/O | Removes filesystem range lookup; still uses kernel block/NVMe stack | Needs a dedicated unmounted device for a valid comparison |
| NVMe passthrough / `io_uring_cmd` / xNVMe | Submits NVMe commands via the generic namespace interface; application owns block placement/metadata | Unmeasured; requires a storage ownership/recovery design and a separate test device |
| SPDK native NVMe driver | Userspace queues and polling with a userspace-bound controller | Unmeasured; cannot rebind this boot/root controller; needs dedicated hardware and resource/provenance review |
| Native GPUDirect Storage | Supported-platform storage DMA into GPU memory through GDS | NVIDIA documents Spark compatibility mode only; not an available Spark option |
| cuFile compatibility mode | Convenient API with an emulated transfer path | Measured separately; API name does not establish native GDS or absence of copies |

No raw disk was written, reformatted, unmounted, or rebound. The kernel's
FIEMAP contract explicitly disallows using extent locations to access a
mounted filesystem through its block device, including reads. Therefore a
same-file/same-block experiment on this mounted root disk would not be a
sound basis for choosing the storage format. No raw-block performance number
is claimed. A spare unmounted device would permit a matched direct-file/raw
comparison and passthrough/SPDK investigation without changing the boot disk.

The PCIe link's encoding-only ceiling is **15.754 GB/s**
(`32e9 * 4 * 128/130 / 8`), before transaction overhead. Comparing a measured
file path with this computed ceiling can bound remaining bandwidth opportunity;
it cannot establish the latency difference versus a raw implementation.
