# Qwen-Image-2.1 reference experiment

This is an external reference experiment on `spark`, not native llmpalooza image
support or evidence that GGML can execute this pipeline. The checkpoint and
reference implementation were inspected on 2026-09-22. Measurements and their
limits are recorded below; raw images, traces, logs, and state stay outside Git.

## Identity and scope

`pins.json` records the immutable checkpoint revision and each downloaded
file's size and SHA-256. The complete selected snapshot is 33,131,614,782 bytes;
that is file storage, not peak physical memory. `dependencies.json` records
the selected Python dependency versions and installed license declarations.
`requirements.txt` freezes those reference packages; `Dockerfile` uses the
same digest-pinned ARM64 base as the earlier llama.cpp reference.

- Checkpoint: `Qwen/Qwen-Image-2.1` at
  `790c92633540aa0cb11d9abf19eb46d861714758`.
- Diffusers: `8b3c707ebd3ec4881f4190cf42931da07eaf3b65`.
- PyTorch: `2.14.0+cu130`; Transformers `5.17.0`; Accelerate `1.15.0`;
  Torchvision `0.29.0+cu130`; Pillow `12.3.0`. The Qwen3-VL processor requires
  Torchvision even in these image-only cases. No checkpoint Python or remote
  custom pipeline is loaded.
- Pipeline: BF16, batch one, seed 42, explicit square size and step count,
  `true_cfg_scale=1.0`, no prompt rewriter. Prefix caching is explicitly set.
  No model CPU offload: on Spark it would consume the same physical budget.
- Text-to-image prompt: `A red ceramic teapot on a plain wooden table, soft
  daylight, no text.` Editing uses a deterministic 256×256 RGB fixture: a
  central red square on a pale background. Its pixels are generated by the
  harness, fingerprinted, and supplied without external user images.

The [pinned model card](https://huggingface.co/Qwen/Qwen-Image-2.1/blob/790c92633540aa0cb11d9abf19eb46d861714758/README.md)
describes the visual generation component as 7B parameters. This is not the
whole pipeline: the model index also selects a Qwen3-VL text encoder and a VAE.
Execution accounting below counts the actual instantiated components.

The owner also supplied a [GGUF comparison candidate](../model-candidates.md).
It is a separate quantized denoiser experiment; the BF16 measurements and pins
here remain the baseline.

## Method and interpretation

`fetch.py` downloads to exclusive temporary files, checks hashes before
promotion, and skips already verified files. `measure.py` rejects unexpected
files and symlinks, rechecks every hash, and explicitly selects local
safetensors. Use a private destination directory; this is not a hardened
service for directories concurrently modified by another user.

Hash verification reads all weights before the load timer. Consequently these
are **post-verification loads**, not cold-storage measurements. Process I/O
counters cover only the measured process; system counters in switching include
other host activity. Neither is a measurement of GPU DRAM traffic.

Instrumented runs synchronize component boundaries and denoising callbacks.
They report parameter/buffer bytes, allocator peaks, live latent and prefix
KV sizes, component call durations, and transformer-block invocation counts.
Repeated block invocation demonstrates repeated logical dependency on weights;
it does not count physical DRAM reads. Allocator peak minus parameter bytes
is not an isolated workspace measurement: it can include live state,
temporary tensors, allocator effects, and buffers. CUDA allocations and host
available-memory observations are complementary views, not additive budgets.
Uninstrumented `--plain` runs provide end-to-end controls and image pixel hashes.
Component peak fields are cumulative request allocator peaks observed at those
boundaries, not independently isolated component workspaces. Device-placement
time wraps `pipe.to("cuda")` plus synchronization and can include allocation,
copies and page faults; it must not be attributed to disk bandwidth alone.

Correctness comparisons keep size, steps, seed, cache mode, prompt, and input
fixed. The [pinned pipeline](https://github.com/huggingface/diffusers/blob/8b3c707ebd3ec4881f4190cf42931da07eaf3b65/src/diffusers/pipelines/qwenimage21/pipeline_qwenimage21.py)
explicitly documents different rounding with prefix caching enabled versus
disabled. Cache-on/off images are therefore separate configurations, not a
bitwise equivalence test or an invented numerical tolerance.

Cancellation requests are injected after a synchronized completed step.
The interrupted pipeline returns latent output. Standalone runs destroy the
whole pipeline, synchronize, collect objects and empty the allocator cache.
The resident suite instead retains weights, cleans request objects, and verifies
the next request against its pre-cancellation pixel control. Each report states
whether the pipeline was retained or released; the suite records a separate
final release. Neither tests cancellation of pending GPU work. No partial image
is classified as a completed generation.

The suite's last, destructive phase-release case synchronizes after prompt
encoding and discards text-encoder backing with `to("meta")`; after the final
completed denoising step it similarly discards denoiser backing before VAE
decode. Metadata remains, but those weights cannot execute again without
reloading. It compares final pixels to the all-resident control. All weights
were initially loaded, so this probes safe release boundaries, not admission
under a smaller initial budget or a successful later reload.

`switch.py` reuses the pinned llama.cpp router harness. It compares resident
text, full text unload plus state restoration, and full text unload plus
recomputation, with the same intervening image request. A short synthetic
continuation stays under 1024 tokens. Resident and restored results must match
the resident token control; recomputation has an independent full-prefill
control with `cache_prompt=False`, and its comparison to resident tokens is
reported separately. Restore must process only the suffix and at most one cached
tail token. This deliberately does not generalize past Gemma's known
long-context rollback/coverage failure (RE-007). There is no forced physical
pressure, partial eviction, or claim of llmpalooza's eventual switching speed.
The outward measurement includes image-process startup and checkpoint hash
verification, model loading and image generation; it is not a serving API
latency. The restore arm also includes a fresh durable text-state save.
Return timing starts after the image process has exited, then includes text
loading/restoration or recomputation through the first generated token.

## Component accounting

The instantiated BF16 reference contains 16,219,988,836 parameters:

| Component | Parameters | Parameter bytes | Registered buffer bytes |
| --- | ---: | ---: | ---: |
| Qwen3-VL text encoder | 8,767,123,696 | 17,534,247,392 | 656 |
| Single-stream denoiser | 7,115,124,736 | 14,230,249,472 | 512 |
| VAE | 337,740,404 | 675,480,808 | 0 |

These counts exclude allocator fragmentation, runtime libraries, activations,
prefix KV and latent state. Stored VAE tensors occupy more bytes than their
BF16 execution form; file storage and execution residency are distinct.

## Measured image results — 2026-09-22

Host: `spark-c4e2`, NVIDIA GB10, driver 580.178.04, kernel
7.0.0-1019-nvidia, 121.69 GiB visible physical memory. The twelve-case suite
loads one pipeline and reuses it across requests; each table cell is one
observation, not a latency distribution. Detailed reduced evidence is in
`aggregates.json`. Initial pipeline loading took 207.122 seconds, including
0.563 seconds in `from_pretrained`; the remainder is device placement and
synchronization. Integrity verification and Python imports precede that timer.

| Case | Generation seconds | CUDA request peak, GiB | Target latent, KiB | Prefix KV, MiB |
| --- | ---: | ---: | ---: | ---: |
| Text, 512², 4 steps, instrumented | 1.459 | 31.919 | 128 | 12.5 |
| Text, 512², 4 steps, cache disabled | 1.425 | 31.906 | 128 | 0 |
| Text, 1024², 4 steps | 6.294 | 36.840 | 512 | 12.5 |
| Text, 1024², 40 steps | 52.586 | 36.840 | 512 | 12.5 |
| Text, 2048², 40 steps | 252.796 | 56.521 | 2048 | 12.5 |
| Edit, 512², 4 steps, first/repeat | 2.750 / 2.076 | 32.423 | 128 | 525 |

The first uninstrumented 512² request took 2.193 seconds; its resident repeat
took 1.427 seconds. All same-configuration 512² text outputs, including the
instrumented and post-cancellation requests, matched exact RGBA pixel bytes.
The cache-disabled text case also happened to match on this input; that does
not override the upstream warning for other inputs/configurations. Repeated
editing matched exactly. All instrumented target latents were finite. The
1024²/40-step image was visually inspected and depicts the requested red
teapot; this is not a general image-quality assessment. Editing conditions
are resized to the selected resolution. Condition-image latents and text
embeddings are included in allocator peaks but not separately isolated in the
target-latent column.

Every one of the 32 denoiser blocks executed on every denoising step. With
prefix caching enabled, the first denoiser call extracted prefix K/V and
subsequent calls reused it. The encoder runs once per request; this is
cross-step prefix reuse, not cross-request prompt caching. The short text
case does not demonstrate a meaningful cache speedup; the edit case has a
much larger measured cache, but no matched cache-disabled edit timing is claimed.

Cancellation after completed step one returned in 1.215 ms and completed
request cleanup in 84.908 ms while retaining weights. The following full
request matched the pre-cancellation pixels. This excludes cancellation while
GPU work is still pending and does not establish image-step save/restore.

The final phase-release request also matched exact pixels:

| Completed boundary | CUDA allocated before → after, bytes | Release seconds |
| --- | ---: | ---: |
| Prompt encoding: discard text encoder | 32,496,800,256 → 14,948,988,416 | 0.197 |
| Final denoising step: discard denoiser | 14,962,489,344 → 732,222,976 | 0.160 |

After complete suite cleanup, PyTorch still reported 33,554,432 bytes allocated
and reserved; this is residual process/runtime allocation, not zero occupancy.
The process then exited. These boundaries suggest useful component-level
reclaim opportunities: encoding weights can become eligible before denoising,
and denoiser weights before decoding. The hot denoiser is repeatedly needed
between steps. Native completion tracking, actual VMM extents, lower-budget
admission, restore, pending-work cancellation, and GGML support remain unproven.

## Text → image → text results

The text checkpoint and llama.cpp identity are the existing reference-aba pins.
Each successful row is one cycle using a 639-token continuation. The saved
prefix contains 627 tokens and occupies 141,268,896 bytes. The image request is
the same 512²/4-step fixed-seed configuration in every row.

| Text policy | Outward harness seconds | Image load / generation seconds | Return to first token, seconds | Prompt tokens processed |
| --- | ---: | ---: | ---: | ---: |
| Keep resident | 128.456 | 103.123 / 3.145 | 0.044 | 12 |
| Unload; restore saved state | 215.118 | 186.267 / 2.189 | 3.103 | 12 |
| Unload; recompute (separate diagnostic) | 257.335 | 234.105 / 2.180 | 4.155 | 639 |

Resident and restored text token arrays match the resident control; their
image pixels also match the standalone reference exactly. **The original
recompute arm failed the resident-token comparison.** Its image was still
identical. A subsequent diagnostic compared fresh-context full prefill before
and after image generation: those text outputs match each other, but differ
from the resident continuation at 15 of 32 generated positions, starting at
zero-based position 17. Thus the differing text trajectory is reproducible
without image generation. This does not establish its numerical cause or
make cached and recomputed text equivalent. No tolerance is invented; see
RE-008. The aggregate explicitly preserves the failed cross-mode comparison
and identifies the separate matched-configuration diagnostic.

The restore arm's timed durable save took 0.107 seconds. No swapping or OOM
counter increments were observed in the three recorded cycles. Sampled
maximum host total-minus-available memory was 65.81 GiB for concurrent text
residency and 42.95/43.51 GiB for restore/recompute. These are 50 ms sampled
host observations, not CUDA allocation sums or enforced budgets. Concurrent
residency was tested only at 512²/4 steps; do not extrapolate a supported
combination at larger resolution.

Outward timings include verification/import overhead and have highly variable
device-placement cost. They are not an isolated retention-policy speedup or
an acceptance floor for llmpalooza. There is no cold-cache or forced-displacement
control, latency distribution, or larger-than-memory image workload here.
The bounded result establishes a standalone reference and useful release
boundaries; native image backend/API scope and delivery milestones remain
separate decisions. Existing image-input API scope does not imply image output.

## Reproduction

Keep models and outputs in a private external directory. On an ARM64 Spark,
build this directory's Dockerfile with an explicit `linux/arm64` platform,
and record the resulting local image identity. Copy `fetch.py`, `measure.py`,
`suite.py` and `pins.json` into the external directory and mount it at
`/experiment`; provide GPU access through the existing NVIDIA CDI
configuration. No network listener is required for image generation.

Recipe validation (2026-09-22, `spark`): a fresh ARM64 build, `pip check`,
pipeline import and GPU arithmetic smoke passed. The local image ID is
`sha256:700d6668940ef01c8ae3fca507618544f514cb63aabcbe245c43cd1092f48781`;
it is not a published pullable image. The full measurements used a separately
assembled container with the same base and package versions; the rebuilt
image was smoke-tested, not subjected to a second full measurement suite.

Run `fetch.py MODEL_DIRECTORY` on the host. With `/experiment` as the working
directory inside the image container, run the standalone cases or the suite:

```sh
python3 measure.py /experiment/model /experiment/t2i-512-4 --size 512 --steps 4
python3 measure.py /experiment/model /experiment/t2i-512-4-plain --size 512 --steps 4 --plain
python3 measure.py /experiment/model /experiment/edit-512-4 --size 512 --steps 4 --edit
python3 measure.py /experiment/model /experiment/cancel --size 512 --steps 4 --cancel-after 1
python3 suite.py /experiment/model /experiment/suite
```

Output directories must not exist. For switching, preserve sibling
`reference-aba/experiment.py` and `artifacts.json` when copying tools to the
host. Set `DOCKER='sudo -n docker'` if needed and run `switch.py` with the
verified text-model directory, a new external output directory, and
`--image-container NAME`; this must be a **dedicated experiment container**
mounting the image experiment at `/experiment`. Failure or interruption stops
that entire container to terminate pending GPU work. The helper binds the text API to loopback with an ephemeral key
and removes its text container on exit. Stop/remove the image container after
the experiment. Remove external generated images and state when no longer
needed; no automatic retention service is installed.

Workstation harness checks:

```sh
python3 -m unittest discover -s docs/experiments/image-reference -p 'test_*.py'
```
